Kirby's Adventure · NES · deterministic emulator · 10 Nov 2026

How an agent drives a game to a behaviour you describe

You say what should happen, in words or as a list of conditions on the game's state. The agent returns a replayable input file that makes it happen, checked on a fresh replay. This page is the recipe, the path to it, and the footage.

Where it started

A $154 experiment that finished the game and left a recipe

On 8 and 9 November an agent built on the Claude API played Kirby's Adventure on a headless emulator: savestates, RAM access, a beam search over button sequences, and a tool loop where the model looked, searched and applied. It produced six verified traces and a per-game recipe.

137,712frames to the ending, replay verified (the first 78,090 are a human TAS replayed)
1.75–2.8×the reference TAS's length, on worlds the agents played from scratch
≈3model turns per room: map dump, a search with a hand-written score, apply
606–1,161turns per long run, $14–$100 each

Its own controller comparison had already settled one question. A cheap decision model (Jev) fed game state died or timed out in three of three rooms; a tiny cloned model did better for nothing; plain search beat both. Models should not press buttons.

The audit

I replayed all six traces from power-on in fresh processes. Every one ends in the state the report claims. Four things were wrong or missing:

  • A variable that lies. stage stays 0 inside every stage of world 1. My first task file used stage == 1 and could never have passed.
  • An object list that hid half the objects. It showed only things with an enemy collision class. Warp Stars, pickups and the UFO in the secret room have class 0. This is why the first session kept asking for "a room view that lists Warp Stars".
  • One proposed optimisation was already done. The built-in search cuts its result at the goal frame.
  • Two "completed" traces ended on their last life or the one before. Fine for progress, wrong for a test or a demo. Tasks now say what must never happen.

What changed

Three changes, in order of how much they bought

1. The search stopped needing a score

The old loop spent its turns on score design. Every room needed a formula that rewarded progress toward a door the model had to locate first, and a bad formula cost one to three stalled two-minute searches. The new search takes a goal and a notion of "a different situation", and explores.

Goal

room not in (43, 44, 45)

A condition on state. "Somewhere new" is a valid one: this found 1-1's invisible door in 16 s with no coordinates.

Cell

(x//8, y//16, nstar)

What counts as a different situation. Put the mechanic's state in it.

Avoid

hp != 47 or ability != 23

Everything that must survive: no damage, keep the ability, stay in the room.

Actions

R*8 · U*5 .*3 · B*24 · L*2

Eight-frame moves, plus the hold, press or fine step this goal needs.

Those four are the model's whole job during a search. A chain command repeats "reach a room not seen yet" until a condition holds: one call carried UFO Kirby through three rooms to the end of the stage.

2. The harness became a coding-agent session

The first session ran a purpose-built API loop with episodes, notes, handoffs and a spend limit. All of that manages context, and a coding agent already does. The driver is now a stateless command, kt: each call opens the run directory, does one thing and saves. Any agent with a shell can use it, including a Sonnet subagent on a subscription plan, and nothing idles or leaks between calls.

# the whole UFO-room trace, as I drove it: five calls
kt new ufo --from 1-1-speed:r44_start
kt search ufo --goal "room not in (0, 42, 43, 44, 45)" --avoid "hp != 47" --apply   # finds the invisible door
kt search ufo --goal "ability == 23" --actions B*24 D*6 R*8 L*8 ... --apply            # inhale, swallow
kt go ufo --until "room == 42" --avoid "ability != 23 or hp < 31"                     # three rooms as a UFO
kt search ufo --goal "room == 0" --cell "(room, frame//30, y//16)" --apply && kt check ufo tasks/secret-ufo.md

3. Checks that catch what the model gets wrong

  • Predicate lint. Dry-run a task's conditions on traces whose behaviour is known. It would have caught stage == 1, and it did flag a step that already held inside a start prefix. I ignored that warning and a subagent caught the consequence, so the checker now judges steps only after the start.
  • A cheap second pair of eyes. State says where Kirby is; it does not say the screen shows the thing. A general vision model at $0.000025 a frame answered four of four acceptance questions correctly ("do the blocks spell a word?", "is there a star on the pillar?"). Jev scored two of four by answering no to everything.
  • Simplify. Delta debugging on inputs: delete, shorten or merge button holds while the trace still passes its whole task. On the HAL trace it removed 40% of the input changes and 6% of the frames, and the result still passed. It makes a trace readable; it does not make it fast.

The recipe

Eight steps, three actors

model decides what things mean. search finds inputs. checker replays and judges. No step has the model choosing inputs frame by frame.

  1. Orient checker

    Run the same input file twice in two processes and compare state hashes. List what exists: verified traces to start from, a knowledge base, named state.

  2. Write the task model

    Ordered conditions on named state, plus conditions that must never hold. Start from the longest verified trace the task allows.

  3. Lint the conditions checker

    Evaluate them on traces you understand. A condition that never holds where it should is wrong before any search runs.

  4. Find the state the mechanic lives in model

    Mark, act, diff. Object tables, counters, the camera. Name it. This is the step that turns a guide's sentence into something a search can use.

  5. Search each step search model

    Goal, cell, avoid, actions. One call per sub-goal. When a search fails, look before searching again.

  6. Check and verify checker

    The conditions hold in order on a replay from the start in a fresh process, and that replay's state equals the live one.

  7. Look model

    A contact sheet of the moment the trace is about. Unattended, a cheap vision model answers a yes/no question per key frame.

  8. Finish for the purpose search

    A speedrun gets a scored beam on the segments worth it. A test trace gets simplified. A demo gets smoothed and a pause on the shot that matters. Then it goes in the library.

Beyond the emulator

What the target has to offer, and what happens without savestates

levelthe target canwhat you get
L0 replayrun an input file from a fixed start, deterministically; dump state and a picture at chosen framesverified traces and the whole loop, at seconds per probe
L1 stepadvance one frame at a time with state readable every frameper-frame conditions, events, mark-act-diff in one call
L2 snapshotsave and restore state in memorysearch at tens of thousands of frames per second

Kirby on an emulator is L2. Fortune Summoners running inside OpenSummoners' deterministic host is L0: the retail game replays an input trace identically, but every probe starts from boot.
